> 这一版解决三个"原型感"最重的问题：控制台要手点、告警之间没有关系、规则写死在代码里。
> 对应代码：`backend/stream_engine.py`、`backend/correlation.py`、`backend/rule_dsl.py`、`rules/*.yaml`

## 一、实时流：从"点一下出一点"到"一直在跑"

### 之前的问题

前端 `setInterval(fetchBatch, 2500)` 定时拉 `/api/simulate`。这有三个毛病：

1. **节奏被前端控制**。后端不是"在持续监测"，而是"被前端问一次才生成一次"。这在架构上是错的——NIDS 的检测节奏应该由流量决定，不由浏览器决定。
2. **前端要自己算增量**。每次拿到 20 条新数据，得自己去重、自己算攻击数、自己维护趋势数组。
3. **断线无感知**。请求失败只是 catch 一下，用户不知道"其实已经断了"。

### 现在的做法：SSE

```
后台线程（StreamEngine） --每秒 N 条--> 检测 --> 落库 --> 关联 --> 广播
                                                              ↓
                                            每个 SSE 订阅者一个有界队列
                                                              ↓
                                              EventSource 长连接推给浏览器
```

为什么选 SSE 不选 WebSocket：

| | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务端→客户端） | 双向 |
| 协议 | 就是 HTTP，代理友好 | 需要 Upgrade 握手 |
| 断线重连 | 浏览器原生自动重连 | 要自己写 |
| 本项目需要 | 只要下行推送 | 用不上上行 |

检测结果只需要"推下去"，客户端不需要往这条连接上发东西（启停、改流速走普通 POST）。用 WebSocket 属于杀鸡用牛刀，还要自己处理重连和心跳。

### 关键实现细节

**有界队列**：每个订阅者一个 `Queue(maxsize=200)`，满了丢最旧的。

```python
try:
    q.put_nowait(payload)
except queue.Full:
    q.get_nowait()      # 丢最旧
    q.put_nowait(payload)
```

为什么？一个卡住的客户端（比如浏览器标签被挂起）如果不丢数据，服务端内存会被它一个人吃光。监控系统的推送通道必须是"可丢弃"的——丢掉的是实时性，不是正确性（数据已经落库了，前端重连后可以拉历史）。

**心跳**：`q.get(timeout=15)` 超时就发一行 `: keepalive`。注释行不触发 `onmessage`，但能防止中间代理把空闲连接掐掉。

**单实例保护**：启动前先 `bind` 一次端口，被占就直接退出。这不是洁癖——开发时踩过坑：旧进程没死透，新进程绑不上端口但**实时流照跑**，两条流同时往一个 SQLite 里写，告警数翻倍，排查了半小时。

### 攻击"战役"模型

如果每个事件都随机挑源 IP，那么同一个攻击源永远不会出现第二次，关联引擎永远只能聚出"1 条告警的事件"，降噪比恒等于 1.0——等于白做。

所以实时流里加了战役模型：一轮战役 = 一个源 + 一个目标 + 一条按杀伤链推进的路径。

```python
CAMPAIGN_PATH = ["port_scan", "brute_force", "dos", "exfiltration"]
# 随机起点 + 随机长度 2~4 段，每段 6~14 条连接
```

战役之间留 6~18 个事件的平静期，否则控制台上永远在"被打"，不像真实网络。背景流量占 45%。

这个模型让控制台上能真的看到"某个 IP 先扫端口、再爆破、最后外传"的完整过程——**这是演示时最有说服力的一段**。

## 二、告警关联：把 300 条红点压成 8 个事件

### 为什么需要

一个端口扫描会命中几百条规则。运维看到的是一屏红点，真正紧急的那条被淹掉。真实 SOC 里这叫**告警疲劳（alert fatigue）**，它不是体验问题，是**漏报问题**——人会对红点脱敏。

### 聚合规则

```
同一 src + 10 分钟滑动窗口内的告警 → 归并为一个 incident
```

选 src 而不是 (src, dst) 的理由：攻击者换目标是很常见的（横向移动），但源相对稳定；按 (src,dst) 分会把一次攻击拆成好几个事件，反而增加噪声。

### 攻击链推断

只保留本项目**能观测到**的 4 个阶段，不假装覆盖完整杀伤链：

| 攻击类型 | 阶段 | MITRE 战术 |
|---|---|---|
| port_scan | 侦察 | Reconnaissance (TA0043) |
| brute_force | 初始访问 | Initial Access (TA0001) |
| dos | 影响 | Impact (TA0040) |
| exfiltration | 外泄 | Exfiltration (TA0010) |

事件上记录"已经走到哪几个阶段"，按顺序渲染成链条。走到"外泄"的事件，风险分天然更高。

### 风险打分

```python
base          = {critical: 40, high: 30, medium: 20, low: 10, info: 5}
stage_bonus   = 15 * (阶段数 - 1)
volume_bonus  = min(25, 5 * log2(告警数 + 1))
score         = min(100, base + stage_bonus + volume_bonus)
```

为什么不用"告警条数"直接排序？因为一个刷了 500 条的低危扫描会盖住一个只有 12 条但已经走到外泄的攻击。**严重度和阶段跨度必须压过数量。**

用 `log2` 而不是线性，是为了让"从 10 条涨到 100 条"和"从 100 条涨到 1000 条"的边际收益递减——数量不是线性重要的。

### 降噪比

```
compression_ratio = alerts / incidents
```

控制台上直接显示 "302 条告警已归并为 8 个攻击事件，平均每个事件 37.8 条（降噪 97%）"。这个数字就是这一模块的价值证明。

### 状态流转

`open → investigating → closed`。已关闭的事件不再接收新告警（同源再来会新建事件），这样"处理完又复发"能被看见，而不是悄悄被并进旧事件里。

## 三、规则 DSL：规则是数据，不是代码

### 之前的问题

```python
if features["syn_rate"] > 0.8 * k and features["packet_count"] > 400 * k:
    add("SYN洪泛特征", "dos", 0.95)
```

五个 `if` 写死在 `detector.py` 里。加一条规则要改代码、跑测试、重新发版。安全运营里规则一天可能改十几次，这个流程跑不动。

导师一句"加条新规则要改代码？"就能问穿。

### 现在的做法

规则写在 `rules/*.yaml`：

```yaml
- id: DOS-001
  name: SYN洪泛特征
  attack: dos
  severity: critical
  confidence: 0.95
  attck: T1498.001
  attck_name: Direct Network Flood
  description: 连接内 SYN 占比超过 80% 且包量巨大
  tags: [flood, tcp, syn]
  window: 1s
  condition:
    all:
      - field: syn_rate
        op: gte
        value: 0.8
      - field: packet_count
        op: gte
        value: 400
```

改完文件调 `POST /api/rules/reload`，或者干脆不动——`RuleSet` 每 2 秒检查一次文件 mtime，发现变化自动重载。

### 条件树

支持 `all` / `any` / `none` 三种组合子，可嵌套：

```yaml
condition:
  all:
    - field: packet_count
      op: gte
      value: 500
    - any:
        - field: syn_rate
          op: gte
          value: 0.9
        - field: bytes_per_packet
          op: lte
          value: 60
```

运算符：`gt / gte / lt / lte / eq / ne`，外加两个比值运算符 `ratio_gte / ratio_lte`：

```yaml
- field: src_bytes
  op: ratio_gte
  value: {other: dst_bytes, factor: 20, floor: 1}
# 语义：src_bytes >= 20 * max(dst_bytes, 1)
```

比值运算符是必需的——"上行是下行的 20 倍"这种判据用常量运算符表达不出来。

### 灵敏度缩放

原实现里 `k = 1.25 - 0.5*s`，所有阈值都乘 k。搬到 DSL 后，每条叶子条件默认 `scalable: true`：

- 增大类（`gt/gte/ratio_gte`）：阈值 × k
- 减小类（`lt/lte/ratio_lte`）：阈值 ÷ k

这样"灵敏度调高 → 阈值更宽松 → 更容易命中"的语义在 YAML 里自动成立，不需要每条规则手写两套阈值。不想被缩放的条件写 `scalable: false`。

### 错误隔离

一条规则写错不能让整个规则库失效：

- YAML 语法错 → 记入 `errors`，跳过该文件，其他文件照常加载
- 单个规则字段非法（比如 `op` 拼错）→ 记入 `errors`，跳过该规则
- 运行时单条规则抛异常 → 跳过该规则，不影响其他规则

错误通过 `GET /api/rules` 的 `stats.errors` 暴露到控制台，红框提示。**运维能看到"哪一行写错了"，而不是"整个系统不工作了"。**

### 规则库现状

14 条规则，覆盖 4 类攻击：

| 类别 | 条数 | 代表规则 |
|---|---|---|
| DoS | 4 | SYN洪泛、小包洪泛、响应缺失型洪泛、高包速率 |
| 端口扫描 | 4 | 端口离散度、水平扫描、低速隐蔽扫描、探测型高SYN |
| 暴力破解 | 3 | 高频失败登录、持续爆破、字典攻击节奏 |
| 数据外泄 | 3 | 上行流量失衡、大流量单向外传、长连接持续外传 |

每条都标了 ATT&CK 编号。全部规则在正常流量上**零命中**（用 600 条 normal 样本验证），在对应攻击上命中率 > 90%。

## 四、演示脚本（照着点就行）

1. 打开控制台 → 监控台。**什么都不用点**，"已检测连接"自己在涨，状态灯是"接收中"。
2. 看"攻击事件"页：告警数几百，事件数只有几个，降噪比几十比一。
3. 点风险分最高的那个事件 → 右侧抽屉打开：攻击链已经走完"侦察 → 初始访问 → 影响 → 外泄"，下面是几十条原始告警。
4. 点"处理中" → 事件状态变化，列表里状态标签跟着变。
5. 切到"规则库" → 14 条规则带 ATT&CK 编号和条件表达式。
6. 现场改一条规则：把 `rules/dos.yaml` 里 `DOS-001` 的 `packet_count` 从 400 改成 50 → 点"重载规则" → 规则库里的表达式立刻变了，不用重启。
7. 回到监控台，把流速调到 10 条/秒 → 事件页数字涨得更快。

## 五、可能被追问的问题

**Q：为什么不用 Kafka / Redis 做消息队列？**
A：这个系统的定位是单机旁路原型，用进程内的 `queue.Queue` 就够。上 Kafka 的前提是"多探针 + 多消费者 + 需要重放"，这三条现在都不成立。真要做分布式，第一步是流表下沉到 Redis、探针只做采集，而不是先上 Kafka。

**Q：SSE 单机撑得住多少连接？**
A：Flask 开发服务器每个 SSE 连接占一个线程，几百个就吃紧了。生产要换 gunicorn + gevent 或 aiohttp。但这个系统的瓶颈不在推送，在检测——单线程 Python 每秒处理几千条连接就到顶了，推送连接数根本到不了瓶颈。

**Q：10 分钟窗口是怎么定的？**
A：经验值。太短（1 分钟）会把一次持续攻击拆成多个事件；太长（1 小时）会把不相关的活动并在一起。真实 SOC 通常用 5~30 分钟，且会按攻击类型调（扫描窗口短、外泄窗口长）。这里是可配置的（`NIDS_CORRELATION_WINDOW`）。

**Q：为什么按 src 聚合而不是按攻击链相关性？**
A：按 src 是最简单且可解释的基线。更严格的做法是做因果关联（比如"扫描结束后 30 秒内出现的爆破"才算同一条链），但需要更细的时间语义和更多样本验证。当前的实现是**有意的简化**，我在代码注释里写明了。

**Q：规则 DSL 和图数据库/CEP 引擎比差在哪？**
A：差在"跨事件的状态机"。现在的规则都是**单条连接内**的判据；真正的 CEP 能做"5 分钟内失败 20 次然后成功 1 次"这种跨事件模式。这是明确的下一步，不是已经做了的事。

**Q：14 条规则够吗？**
A：不够，但重点不是条数。Suricata 有 3 万条签名，靠的是社区十几年积累。这个项目的价值在于**规则是可扩展的数据结构**，而不是规则有多少条——从 14 条到 140 条只是写 YAML 的工作量，架构不用动。

